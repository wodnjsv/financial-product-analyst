# 질의 명세 검증 전후 비교 실험

**Date:** 2026-11-16

## 결과

잘못된 조회 23건에서, 검증을 끄면 23건(100%) 모두 SQL이 DB까지 실행됐고 검증을 켜면 0건이 실행됐습니다.
정상 질의 20건은 두 조건 모두 SQL까지 실행됐습니다(잘못 막은 것 0건).

| 오류 유형 | 사례 | 검증 끔: DB 도달 | 검증 켬: DB 도달 | 검증 켬: 처리 (코드) |
| --- | --- | --- | --- | --- |
| 상품군 오지정 (`국내 ETF` 질문에 모델이 해외 ETF 선택 등) | 6 | 6 | 0 | 모델 제안 거절 (`MODEL_EXACT_LOCK_CONFLICT`) |
| 상품군 모호 (`ETF 중…`처럼 국내·해외 근거 없이 모델이 하나를 확정) | 6 | 6 | 0 | 확인 요청 (`AMBIGUOUS_PRODUCT_FAMILY`) |
| `또는` 조건 (OR 조건이 AND SQL로 실행) | 5 | 5 | 0 | 제한 안내 (`BOOLEAN_PREDICATE_SCOPE_UNSUPPORTED`) |
| 실행 직전 SQL·인자 변조 (기준값·상품군·LIMIT·WHERE·지표·데이터 버전) | 6 | 6 | 0 | 실행 거절 (`EXECUTION_REQUEST_REJECTED`) |
| **오류 합계** | **23** | **23 (100%)** | **0 (0%)** | |
| 정상 (국내·해외 ETF 총보수 조건·순위, 1년 수익률 순위, 채권 만기일 조건) | 20 | 20 | 20 | |

검증을 끈 조건에서 실제로 실행된 SQL을 확인했습니다.

- 상품군 오지정 6건은 질문과 다른 상품군으로 조회했습니다.
- `또는` 조건 5건은 `총보수 <= 0.1 AND 총보수 >= 0.5`처럼 동시에 만족할 수 없는 조건으로 실행돼, 질문에 맞는 상품이 결과에서 빠졌습니다.
- 변조 6건은 바뀐 기준값(0.1 → 1.0), 상품군, LIMIT(5 → 50), `WHERE TRUE OR …` 등이 그대로 실행됐습니다.

## 실험 방법

- 모델 제안: `tests/intent/test_personal_intent.py`의 가짜 어댑터로 고정했습니다. 오류 사례는 어댑터가 틀린 상품군이나 근거 없는 상품군을 고르게 했습니다. NVIDIA, PostgreSQL, 원천 데이터는 호출하지 않습니다.
- DB: 가짜 러너가 받은 SQL을 기록한 뒤 실행을 멈춥니다. 지표는 "SQL이 DB에 도달했는가"입니다. 결과 행 검증(03번 실험)은 이 지표와 무관합니다.
- 검증 켬: 현재 경로 그대로입니다.
- 검증 끔: 다음 네 검증만 통과하게 바꿨습니다. 나머지(계약 완결성, 계획 pin, 정의 버전 등)는 두 조건이 같습니다.
  1. 질문에 명시된 상품군 고정: `build_exact_semantic_locks`에서 상품군 고정을 뺌
  2. 상품군 모호성 검사: `ambiguous_product_family_frames`
  3. `또는` 조건 검사: `unsupported_boolean_frames`
  4. 실행 직전 재컴파일 대조: `SemanticSqlCompiler.validate_request_for_execution`
- 변조는 컴파일이 끝난 실행 요청을 실행 직전에 바꾸는 방식으로 넣었습니다.

재현:

```bash
PYTHONPATH=.:src python scripts/run_query_validation_ablation.py > ablation.json
```

출력의 `summary`가 위 표의 숫자이고, `cases`에 사례별 실행 SQL의 상품군·기준값과 처리 코드가 있습니다.

## 한계

- 사례는 이 네 검증이 겨냥한 오류 유형에 맞춰 직접 만든 합성 사례입니다. 이 숫자는 실제 모델이 이런 오류를 얼마나 자주 내는지가 아니라, 냈을 때 막는지를 보여줍니다.
- `기간 누락`(예: `국내 ETF 수익률 높은 5개`)은 포함하지 않았습니다. 기간이 없으면 연결할 지표 정의가 없어 검증을 꺼도 실행할 SQL이 만들어지지 않으므로, 끔/켬 비교가 성립하지 않습니다. 이 경우는 기존 단위 테스트로 확인 요청을 검증합니다.
- 상품 지정 누락, 기준일 이후 요청 등 `_route` 안의 다른 차단은 따로 끌 수 있는 함수가 아니어서 이번 비교에 넣지 않았습니다.
- 가짜 러너는 SQL을 실행하지 않으므로 응답 시간이나 결과 정확도는 측정하지 않았습니다.
